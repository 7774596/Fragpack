# NativeCodec 与真实 LMCache L1 接入验证（2026-11-01）

状态：接入、功能检查、四次主模型对照、两次不可变 KV 往返和补充输出路径核验均已完成。
外部容量收益成立，当前 CPU/RPC 恢复路径仍拖慢 TTFT。

开发分支为 `feat/native-attention-external-codec`，基线提交 `a5ddb75084c9`。
实验使用该基线上的本轮改动，主对照全程冻结源码；具体文件哈希保存在

## 实现与范围

`FragPackNativeConnector` 使用 vLLM 公开的 KV connector 接口。
原生 GPU KV 保持 BF16，prefill、decode、KV 写入和 FA3 均由原版 vLLM 执行。
prompt 中的完整块在请求结束后通过 `NativeBlockTransfer` 编码、传到真实 LMCache CPU L1，
恢复时直接解码到原生目标页。未改第三方源码，不使用 CUSTOM attention 或 runner 包装。

编码前存在性检查和同 key 在途合并仅减少重复工作，Raw 对照也启用相同规则。
外部副本被淘汰后可再次保存；没有新增淘汰策略、预测预取或 NVMe 支持。
编码与恢复工作区分别有界，源页读取完成和外部发布完成为两个独立完成点。

压缩使用 FPKB；Raw 使用明确标记的 FPNR token-major 格式和独立身份空间。
两组使用同一个字节 RPC 接口。Raw 是匹配接口的对照，不代表原版 LMCache
最优的零拷贝 Raw 路径。该方案不增加活跃 GPU KV 的容量。

## 已完成的功能检查

环境为 H800 PCIe（GPU 2），vLLM 0.30.0+cu129、PyTorch 2.13.0+cu129、
LMCache 0.5.6，TP=1、V2 runner、eager、BF16 KV、原生 FA3。
GPU 检查均在独占条件下执行，结束后释放。

- 156 项 CPU 检查通过，覆盖身份/格式、跨缺口探测、有界池、失败/取消、页所有权与完成通知。
- 6 项 GPU 检查通过，覆盖非连续原生页、Raw/压缩全层 K/V 逐位往返及非法目标。
- Qwen3-0.6B 在真实 LMCache CPU L1 下完成以下五步；两种路径的结果一致。

| 操作 | cached tokens（GPU＋外部） | 实际外部恢复块数 |
| --- | ---: | ---: |
| 首次 513-token 请求 | 0 | 0 |
| 同请求，保留 GPU APC | 512 | 0 |
| 清空 GPU APC 后重放 | 512 | 4 |
| 修改早期 token 后重放 | 0 | 0 |
| 保持前 256 token、修改后部 | 256 | 2 |

冷请求、GPU 命中与外部恢复的生成 token 完全一致；Raw/压缩五步的输出也一致。
两组均无保存/恢复失败、残留任务或完成通知泄漏。20 次块保存机会实际只上传 10 块，
另 10 块在编码前跳过。该小模型使用借用码表，仅作为功能验证，不解释其压缩率或延迟。
证据见[功能摘要](data/native-codec-serving-20261101-functional.json)。

保留了两个开发期问题：首次 CUDA JIT 导致一个等待超时，改为初始化编译后重测通过；
早期 Raw 原型的数值往返正确，但格式标识不匹配实际排列，已改为 FPNR 并补拒绝混用检查。
修复前的性能数据不进入正式对照。

## 正式对照协议

主模型为 Qwen3-30B-A3B-Instruct-2507-FP8，权重 FP8、KV BF16。
GPU 2 在原生模型加载后的可用 KV 预算实测为 **44,674,775,040 bytes**。
两组从该预算中扣除各自 codec、传输、页映射与描述符，再分配原生 KV 页。
LMCache L1 固定 **56 GB**，原版 LRU，触发水位 0.9、淘汰比例 0.1。

固定 24 个各含 32,768 token 的独立历史，按 12 → 18 → 24 个历史逐步扩大工作集；
每阶段首次加入新历史后进行两轮重复访问。每进程共 132 个串行请求，每请求输出 32 token。
正文来自 GSM8K train 的问题与解答，用于构造自然文本历史；这不是 GSM8K 精度测试，
也不是 AgentX 官方负载。主对照不清空 GPU APC。

Raw、压缩各两个独立模型/L1 进程，顺序为 Raw → 压缩 → 压缩 → Raw。
计时包括首次 prefill、生成、编码、D2H、外部发布、后续取回与解码，以及每步保存排空。
模型加载与显式 codec 初始化/JIT 单列，首次请求额外触发的模型 JIT 保留在冷请求计时中。
TTFT/TPOT 取真实 vLLM 请求指标；执行为离线完整模型引擎，
不含 HTTP 前端，不把串行请求吞吐解释为并发服务容量。

另以固定捕获 KV 的真实 L1 往返比较 Raw、压缩、压缩关闭提前探测三组，
正反顺序各一遍。该消融只使用同一份不可变 KV，完整保留首次保存开销；
不能把独立重算产生的同 token KV 假定为逐位相同。

码表来自此前 OpenHands BF16 KV 捕获的前 8 页；主模型当前使用 FP8 权重。
需报告实际 K/V 记录大小和 raw fallback，不能将历史捕获的压缩率直接移作当前模型结果。
执行协议见[设计文档](design/native-codec-serving-validation.md)。

## 主模型容量与时延结果

四个进程均完成 132 个请求，模型、源码、预算、独占 GPU、传输完成和 L1 关闭检查通过。
下表保留每个进程的原值；总窗口为请求生成加发布排空的逐步墙钟之和。
全程回放另有约 0.41–0.44 秒测试工具开销。

| 进程（执行顺序） | 总窗口（秒） | 平均 TTFT（秒） | P95 TTFT（秒） | TPOT 中位数（毫秒） |
| --- | ---: | ---: | ---: | ---: |
| Raw 1 | 1724.68 | 1.566 | 1.892 | 56.08 |
| 压缩 1 | 1281.90 | 2.973 | 7.637 | 56.89 |
| 压缩 2 | 1273.30 | 2.984 | 7.374 | 56.28 |
| Raw 2 | 1702.09 | 1.569 | 1.891 | 56.97 |

按两个进程的中心值比较，总窗口减少 **25.43%**；按同编号两组比较分别减少
25.67% / 25.19%。这包含保存成本的减少，不能写成用户请求加速。
外部恢复使平均和 P95 TTFT 上升；全体请求的 TTFT 中位数约 1.88 秒，反而会掩盖这项代价。
P95 按每进程 132 个请求做 inclusive 线性插值；每模式仅两个独立进程，不据此报告置信区间。

下表合并同一进程内某个历史规模的两轮返回；斜线两侧为进程 1 / 2。
外部命中数量在两个进程中相同。12 个历史时，两种路径均有 24/24 次 GPU APC 命中，
每请求复用 32,640 token，因此外部读取为零。

| 历史数 | Raw 外部命中 | 压缩外部命中 | Raw 返回 TTFT 中位数（秒） | 压缩返回 TTFT 中位数（秒） |
| --- | ---: | ---: | ---: | ---: |
| 12 | 0/24 | 0/24 | 0.122 / 0.122 | 0.121 / 0.122 |
| 18 | 0/36 | 36/36 | 1.885 / 1.885 | 6.875 / 7.091 |
| 24 | 0/48 | 0/48 | 1.885 / 1.886 | 1.884 / 1.884 |

18 个完整历史的对象 payload 为 Raw **58.001 GB**、压缩 **40.843 GB**。
压缩因此保留了此轮所需历史；36 次返回共恢复 9,180 块、81.367 GB，
9,216 次保存候选全部跳过，没有再次编码或上传。
24 个历史若全部保留，压缩需 **54.457 GB**：虽然小于 56 GB 配额，
却超过 **50.4 GB 淘汰触发水位**，顺序循环访问再次发生失命中。
这些命中率对应本次顺序工作集，不能推广为其他访问分布的结果。

主模型 K/V 记录分别为原始 BF16 大小的 **70.74% / 70.04%**；
带对象头的压缩 payload 为 BF16 净 KV 的 **70.44%**。
同一组 24 个历史相对 Raw 归档少 **29.58%**；raw fallback 占 K/V 记录的
**0.0008901%**。每个完整进程上传量为 Raw **348.006 GB**、压缩 **163.372 GB**；
后者还下载 81.367 GB，不能只以上传量代表总搬运量。
整个进程实际 gather/编码块数为 Raw 27,648、压缩 18,432。
外部副本被淘汰后仍会重编码；“只编码上传一次”只对副本保留期间成立。

相同总预算下，Raw/压缩实际分配 **3546 / 3538** 个原生 GPU 块。
辅助 GPU tensor 为 **50.334 / 151.168 MB**，压缩多占 **100.834 MB**；
计入原生页后分别为 44.669340 / 44.669511 GB，均未超过 44.674775 GB 预算。
两组 pinned 池均为 50.348 MB。这条路径改善外部存储容量，活跃 GPU KV 仍为 BF16。

18 个历史的两轮返回合计，两个压缩进程分别用时 **322.034 / 321.769 秒**。
其中 `get` 加 CPU 解包/整理为 **237.227 / 235.444 秒**，约占阶段墙钟的
**73.2%–73.7%**；H2D 加解码/status 计时段为 **6.071 / 8.774 秒**，约占
**1.9%–2.7%**。`get` 包含 L1 读取、字节处理和 IPC，GPU 计时段也含主机提交和同步，
均不是纯网络或纯 kernel 时间。当前主要瓶颈是外部字节传输接口与 CPU 整理。

## 受控不可变 KV 往返结果

48 层、4 KV heads、head dimension 128；64 个逻辑块，每块 128 token，
原始 BF16 共 805.31 MB。码表使用捕获页 0:8，输入为页 8:32 循环至 64 块。
每个独立进程执行三次保存/恢复，保留 L1 副本；逐位比较与目标清零在计时之外。

| 指标 | Raw＋提前探测 | 压缩＋提前探测 | 压缩、关闭提前探测 |
| --- | ---: | ---: | ---: |
| 单轮实际归档 payload（MB） | 805.57 | 567.60 | 567.60 |
| 首次保存（两进程，秒） | 3.211 / 3.105 | 2.734 / 2.821 | 2.475 / 2.445 |
| 后两次保存中位数（秒） | 0.034 / 0.034 | 0.033 / 0.034 | 2.606 / 2.957 |
| 三次恢复中位数（秒） | 2.754 / 2.546 | 1.519 / 1.955 | 1.690 / 1.855 |
| 三次保存＋三次恢复总耗时（秒） | 11.530 / 10.805 | 7.327 / 8.758 | 12.847 / 13.925 |
| 实际 gather/编码块数 | 64 | 64 | 192 |

每格两个数分别来自正序、反序进程；单进程内三轮不是三个独立实验。
数据见[受控往返摘要](data/native-codec-serving-20261101-micro.json)。
压缩归档 payload 比 Raw 小 **29.54%**，K/V 记录分别为原始大小的
70.82% / 70.04%，raw fallback 为零。开启相同提前探测时，完整往返总耗时
在两次进程对照中分别减少 **36.45% / 18.94%**。提前探测避免后两轮重复上传，
这一收益与压缩算法本身分开归因。

当前 `put/get` 调用占总墙钟约 84%–92%，GPU 操作加 DMA 的主机计时段仅占约
1.2%–1.7%；这些计时段包含等待，并非纯 kernel profiling。
RPC 含封装、复制、L1 存取/发布确认等工作；Raw 恢复还有额外 CPU 数据实体化。
所以不能把全部时延差归因于 GPU codec 或 PCIe，也不能推广为原版 LMCache 的性能差距。
`source_hold_seconds` 是逐批从排队到源页可释放的累计值，并非整条请求的页保留时长；
它和排队时间不能直接加到墙钟时间上。scheduler 的 lookup 异常只写日志，
不进入 worker 保存/恢复失败计数，完整性检查需同时检查该日志。
这里的 RPC bytes 是对象 payload，含格式头、不含 ZMQ/协议完整线上字节。
压缩额外占用约 **100.8 MB GPU 工作区**，pinned 池仍按最大大小预留；
传输量减少不等于同等数量的总内存释放。

## 生成输出与后续工作

同模式两个主模型进程的 132 个生成结果均一致。Raw 与压缩在 120/132 个请求中一致；
12 个差异均位于 18 历史阶段，此时 Raw 重算而压缩从外部恢复。
Raw 自身的 24 次 GPU 命中也有 4 次与冷请求输出不同，因此不能直接把跨路径差异归为 codec 损失。

针对六个涉及差异的历史，另起 Raw/压缩模型与 L1 进程，各执行 18 步：
每个历史依次冷算、GPU 命中、清空 GPU APC 后外部恢复。每个命中请求均复用 32,640 token；
GPU 命中外部恢复数为零，外部命中实际恢复 255 块；后两步都跳过 256 次重复保存。

| 输出比较 | 一致历史数 |
| --- | ---: |
| Raw 冷算 vs 压缩冷算 | 6/6 |
| Raw GPU 命中 vs 压缩 GPU 命中 | 6/6 |
| Raw 外部恢复 vs 压缩外部恢复 | 6/6 |
| 同模式 GPU 命中 vs 外部恢复（两模式分别） | 6/6 |
| 同模式冷算 vs GPU/外部命中（两模式分别） | 0/6 |

这些选定历史的差异跟随冷算与缓存计算路径，相同路径未观察到 codec 引入的生成差异。
这是对已出现差异的定向诊断，不是独立性能样本或模型精度测评。
完整结果与输入/输出哈希见[路径核验数据](data/native-codec-serving-20261101-output-control.json)。
不可变 KV 的逐位往返仍是独立的 codec 正确性证据，生成 token 对比不能替代它。

后续优先减少压缩记录在 CPU/RPC 中的封装与复制，并以相同改进后的接口重测 Raw/压缩；
再验证有界缓冲内的编码、DMA 与发布重叠及请求级源页保留时长。
缓存规则保持当前范围。HTTP、并发服务容量、NVMe、TP>1、CUDA Graph 和模型任务精度
仍需单独验证。
